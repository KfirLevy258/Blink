# What the daemon runs against on a customer's machine.
#
# Pinned, not floating. `pip install pyserial esptool` resolves to whatever
# PyPI has on the day someone installs, so a future esptool release would
# break flashing for every NEW install while every existing one kept working
# -- a failure that reaches people who just bought the device and cannot be
# reproduced on any machine that installed earlier.
#
# These two are the versions verified against real hardware on 2026-08-21:
# MCUboot and the app were flashed to an unfused CYD with esptool 5.3.1, and
# the daemon ran the full hello/usage/OTA exchange over pyserial 3.5.
#
# Raising a pin is a deliberate act: re-flash a board with it first.
pyserial==3.5
esptool==5.3.1
# Nothing in pc/ imports this. It is here because esptool 5.3.1 asks for
# bitstring with no upper bound, so pinning esptool still left one version
# floating. bitstring 5.0.0 took BitStream away and made tibs its only
# backend, and on a freshly set-up bench Mac (2026-10-12) espefuse then died
# on import with "cannot import name 'BitStream'" -- tools/lib_efuse.sh read
# that as a busy port and burn.sh refused to flash. tools/build_binary.sh also
# leaves tibs out by name, which is only safe while bitstring is 4.x.
# 4.4.0 is the version esptool 5.3.1 flashed and eFuse-probed a CYD with that
# day. Found by gapietro in their fork.
bitstring==4.4.0
# Verifies the release manifest's P-256 signature before this program will
# replace itself. Pure Python and ~100 KB frozen, where `cryptography` would
# add tens of megabytes to every platform's download to check one signature a
# day. It never touches the usage path, only the update path.
ecdsa==0.19.1
# The CA bundle the update fetch trusts. The frozen macOS binary carries
# python.org's OpenSSL, whose default certificate path exists only on a Mac
# with that same Python installed -- without this, every HTTPS fetch failed
# and no installed device could update (2026-08-29). See pc/ota.py.
certifi==2026.7.22
