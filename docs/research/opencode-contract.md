# OpenCode contract, as of OpenCode 1.19.3

What BLINK assumes about OpenCode and about the GLM Coding Plan's quota
endpoint, and how each assumption was established. The design that rests on
it is `docs/plans/opencode.md`; the CI check that watches it is
`tests/ci/check_opencode_contract.sh`, and every numbered check there points
back to a section here.

Evidence tags: **MEASURED** = observed by running OpenCode 1.19.3 (npm
`opencode-ai@1.19.3`, darwin-arm64, 2026-10-19) in a scratch HOME with every
XDG variable pointed inside it, against a stdlib mock of an OpenAI-compatible
endpoint -- no real model was called, nothing was signed in, no quota was
spent. **READ** = upstream source at tag `v1.19.3` (commit `e3c4eb2`,
2026-10-16) of `github.com/anomalyco/opencode`, which `sst/opencode` now
redirects to. **PROBED** = an unauthenticated request to a live endpoint.
**3P** = reported by a third party; how far to trust it is said each time.

No fixture in this repository was captured from a real machine. The quota
replies the parser is tested against are generated by
`tests/support/opencode_fixture.py`, in the shapes below.

## 1. Where OpenCode keeps things

**One data directory and one config directory, both from xdg-basedir.**
READ: `packages/core/src/global.ts` -- `const app = "opencode"`,
`const data = path.join(xdgData!, app)`, the same for config, state and
cache. xdg-basedir 5.1.0 (the version pinned in `packages/core/package.json`)
is `XDG_DATA_HOME || ~/.local/share` and `XDG_CONFIG_HOME || ~/.config`, with
**no platform branch**. So:

| OS | data (DB, auth.json) | config (plugins) |
|---|---|---|
| macOS | `~/.local/share/opencode` -- not `~/Library` | `~/.config/opencode` |
| Linux | `$XDG_DATA_HOME/opencode`, else `~/.local/share/opencode` | `$XDG_CONFIG_HOME/opencode`, else `~/.config/opencode` |
| Windows | `%USERPROFILE%\.local\share\opencode` | `%USERPROFILE%\.config\opencode` |

The Windows row is READ, not measured on a Windows machine. OpenCode's own
troubleshooting page agrees with it. The v1.2.0 release note says
"%APPDATA% on windows"; that is wrong for the CLI (only the desktop app's
settings live there), and the code is what runs.

`OPENCODE_CONFIG_DIR` adds a config directory and `OPENCODE_DB` moves the
database. Both are variables of the shell OpenCode runs in, which the daemon,
running as a login service, cannot see -- so it does not pretend to honour
them.

## 2. The database

**`<data>/opencode.db`, SQLite, WAL.** READ:
`packages/core/src/database/database.ts` -- release channels (`latest`,
`beta`, `prod`) write `opencode.db`; any other channel writes
`opencode-<channel>.db`; the connection opens with
`PRAGMA journal_mode = WAL`. Since v1.2.0 (2026-02-14) this one file replaces
the `storage/` JSON tree the troubleshooting docs still describe; MEASURED,
1.19.3 writes nothing under `storage/` on a fresh install.

**Most of the data sits in the WAL.** MEASURED: after the lab runs
`opencode.db` was 4 KB and `opencode.db-wal` 836 KB. An mtime check on the
`.db` alone sees nothing happen, which is why BLINK's activity clock takes the
newest mtime of both.

**What the DB cannot say** (MEASURED, all five):

- Session status (`busy` / `idle` / `retry`) is held in memory only.
- A tool waiting on a permission prompt is stored as `status: "running"`,
  exactly like a tool that is executing.
- A retry leaves no trace until every attempt has failed.
- There is no pid, port or lock file.
- A killed OpenCode (`kill -9` during a permission prompt) leaves its message
  marked running forever; a later session does not clean it up.

So the DB is a clock and nothing more. Live state comes from a plugin.

Token counts and cost are in the DB (`session.tokens_*`, `message.data`);
**no limit is**, so there is no percentage anywhere on disk.

## 3. The plugin contract

**Discovery.** READ: `packages/opencode/src/config/plugin.ts` scans every
config directory with `Glob.scan("{plugin,plugins}/*.{ts,js}")`;
`packages/opencode/src/config/paths.ts` puts the global config directory
first in that list, followed by every `.opencode/` from the working directory
up to the worktree root, and `~/.opencode`. MEASURED: a plain `.js` file
importing only `node:` builtins loads with no npm install. OpenCode does run a
background `npm install @opencode-ai/plugin` in each config directory on its
own; that happens with or without our file.

**Shape.** READ: `packages/plugin/src/index.ts` --
`export type Plugin = (input: PluginInput, options?) => Promise<Hooks>`; every
exported function is loaded as one. BLINK uses three hooks:

- `event?: (input: { event: Event }) => Promise<void>` -- every bus event,
  as `{id, type, properties}`;
- `"tool.execute.before"` and `"tool.execute.after"` -- input
  `{tool, sessionID, callID}`, used only to keep a long tool call's clock
  fresh.

`"permission.ask"` is declared in the same interface but has **no call site**
in 1.19.3 (READ) and never fired (MEASURED). The `permission.asked` event is
what fires. There is no shell-command hook configuration of the kind Claude
Code and Codex have.

**Events BLINK keys on** (READ in `packages/schema/src/`; payloads MEASURED):

| event | properties used | source |
|---|---|---|
| `session.status` | `sessionID`, `status.type` = `busy` / `idle` / `retry`; a retry adds `attempt`, `message`, `next` (epoch ms) | `session-status-event.ts` |
| `session.created`, `session.updated` | `sessionID`, `info.id`, `info.parentID` (a subagent's session), `info.directory` | `v1/session.ts` |
| `session.deleted` | `sessionID`, `info.id` | `v1/session.ts` |
| `session.error` | `sessionID` (optional), `error.name` -- `APIError`, `MessageAbortedError`, ... | `v1/session.ts` |
| `permission.asked` | `id` (`per_...`), `sessionID` | `v1/permission.ts` |
| `permission.replied` | `sessionID`, `requestID`, `reply` | `v1/permission.ts` |
| `question.asked` | `id` (`que_...`), `sessionID` | `v1/question.ts` |
| `question.replied`, `question.rejected` | `sessionID`, `requestID` | `v1/question.ts` |

Sequences, MEASURED:

- **A normal turn:** `busy`, then `idle` (and the deprecated `session.idle`).
- **One 429, then success:** `busy`, `retry{attempt: 1, next}`, `busy`, ...,
  `idle`. Nothing about the retry reaches the DB.
- **A quota error:** `retry` five times (`RETRY_MAX_RETRIES = 5`), then
  `session.error`, then `idle`. The wait honours `retry-after-ms` /
  `retry-after`, capped only at 2^31-1 ms, and is otherwise exponential up to
  30 s. A provider sending a long `Retry-After` can hold a session in `retry`
  for hours, and only a plugin sees it. This is why a retry scheduled more than
  60 s out is shown as failed.
- **A 401:** no retry; `session.error` at once.
- **A permission prompt** (via `opencode serve`): `tool.execute.before`, then
  `permission.asked`. `/session/status` still says `busy` while it waits. Then
  `permission.replied`.

`opencode run` auto-rejects permissions and denies the question tool, so a
prompt can only be produced under `serve` or the TUI.

## 4. The credential

**`<data>/opencode/auth.json`, mode 0600.** READ:
`packages/opencode/src/auth/index.ts` --
`const file = path.join(Global.Path.data, "auth.json")`. An API key entry is
`{"type": "api", "key": "...", "metadata"?: {...}}`, keyed by provider id:
`zai-coding-plan` for the global GLM Coding Plan, `zhipuai-coding-plan` for
the mainland one. Those ids come from models.dev (READ,
`anomalyco/models.dev` `providers/*/provider.toml`), where they point at
`api.z.ai` and `open.bigmodel.cn` respectively; the id therefore picks the
host the key may be sent to. `OPENCODE_AUTH_CONTENT` can replace the file;
like `OPENCODE_DB`, the daemon cannot see it.

**This is moving.** READ, `dev` branch, 2026-10-19: OpenCode 2.0 carries the
migration `20260805200742_import_legacy_credentials`, which copies auth.json
into a `credential` table in `opencode.db` (`integration_id` = provider id,
`value` = JSON `{"type": "key", "key": ...}`), and
`packages/opencode/src/auth/index.ts` no longer exists. The table already
exists in 1.19.3's schema, but in 1.19.3 both ways a key gets saved --
`opencode auth login` (`cli/cmd/providers.ts`) and the provider auth flow
(`provider/auth.ts`) -- write through `Auth.set`, which is auth.json (READ).
The day a release
tag registers that migration in `migration.gen.ts`, the contract check fails
with an explanation, and the reader has to learn the table -- a read-only
SQLite query, so still standard library.

## 5. The quota endpoint

```
GET https://api.z.ai/api/monitor/usage/quota/limit           (zai-coding-plan)
GET https://open.bigmodel.cn/api/monitor/usage/quota/limit   (zhipuai-coding-plan)
Authorization: <key>          raw, no "Bearer" -- what Z.ai's own plugin sends
```

READ in Z.ai's `zai-coding-plugins` (`query-usage.mjs`) and CodexBar's
`zai.js`. CodexBar sends `Bearer <key>`; PROBED, both forms are parsed as a
token.

**Failures are HTTP 200.** PROBED, 2026-10-19:

| request | HTTP | body |
|---|---|---|
| no header | 200 | `{"code": 1001, "success": false, "msg": "Authentication parameter not received ..."}` |
| `Authorization: x` | 200 | `{"code": 401, "success": false, "msg": "token expired or incorrect"}` |
| mainland host, no header | 200 | `code 1001`, message in Chinese |

So success is `success === true && code === 200` in the body, never the HTTP
status. That is also why CI cannot check this endpoint: without a key, every
request gets the same `1001`, which says nothing about a real reply.

**A real reply** (3P: posted in CodexBar issue #2724 by a Lite subscriber;
the figures are theirs, not ours):

```json
{"code": 200, "success": true, "data": {"level": "lite", "limits": [
 {"type": "CREDIT_LIMIT", "unit": 3, "number": 5, "usage": 2000, "currentValue": 71,
  "remaining": 1929, "percentage": 3, "nextResetTime": 1786073946574},
 {"type": "CREDIT_LIMIT", "unit": 6, "number": 1, "usage": 10000, "currentValue": 71,
  "remaining": 9929, "percentage": 1, "nextResetTime": 1786660486998}]}}
```

- **The window is `unit` and `number`, never position or type.** Unit 3 is
  hours and 6 is weeks (CodexBar's table `{1: day, 3: hour, 5: minute,
  6: week}`): the five-hour window is `(3, 5)` and the week is `(6, 1)`. Both
  entries share a type, and the order differs between reports.
- **`usage` is the allowance**, `currentValue` what was used, `remaining` what
  is left, `percentage` an integer. The finer `currentValue / usage` is used
  when both are present.
- **`nextResetTime` is epoch milliseconds.**
- **Two plan generations.** Plans bought since the relaunch of 2026-07-30
  (3P, CodexBar #2522) report `CREDIT_LIMIT`. Older ones, still live until
  they expire, report `TOKENS_LIMIT`, sometimes with only `percentage`, plus a
  monthly tool quota `TIME_LIMIT` at `(5, 1)`, which the panel does not draw.
- **The five-hour reset is sometimes about ten hours out** (3P, CodexBar
  #2712 and #2871; CodexBar's fix, PR #3416, drops it). A five-hour countdown
  of nine hours is a confident wrong number; BLINK drops any five-hour reset
  further than 5 h + 60 s away and shows none.

The windows themselves (READ, docs.z.ai `devpack/overview`): five-hour
credits refresh five hours after they are spent, a rolling window; weekly
credits reset every seven days from the order date. Lite is 2,000 / 10,000,
Pro 12,000 / 60,000, Max 28,000 / 140,000. Quota reset cards can restart a
cycle early, which is one more reason to trust only the server's
`nextResetTime`.

Rate-limit errors on the chat API (READ, docs.z.ai `api-reference/api-code`)
are HTTP 429 with a string `code`: 1302 is concurrency, 1308 / 1310 and
1316-1321 are the five-hour and weekly quotas. The reset time is only inside
the message text. BLINK does not parse these; the quota endpoint is the
source, and a long retry is the signal.

## 6. What `dev` already breaks

`sh tests/ci/check_opencode_contract.sh dev`, 2026-10-19, against the 2.0
rewrite on OpenCode's default branch. These pass: the `session.status`
literals and `next`, the session events with `parentID`,
`MessageAbortedError`, and `permission.asked` / `replied`. These fail:

- `global.ts` moved to `packages/util/src/global.ts`. It no longer imports
  xdg-basedir but computes the same `XDG_* || ~/.local/share` roots itself,
  so the paths are unchanged.
- The DB file name moved to `packages/cli/src/database-path.ts`. It is still
  `opencode.db`, and the release channel list now adds `dev` and `next`.
- The v1 plugin loader (`config/plugin.ts`, `config/paths.ts`,
  `config/config.ts`) and the v1 plugin API (`packages/plugin/src/index.ts`)
  are gone. 2.0 has a new plugin API (`@opencode/plugin`, Effect- and
  Promise-based) with its own discovery. **This is the one that matters:**
  `blink.js` will not load under 2.0, and the activity light goes dark until
  the plugin is ported.
- `v1/question.ts` moved to `packages/schema/src/question.ts`.
- auth.json moves into the `credential` table (section 4), and
  `auth/index.ts` is gone. Without a reader for the table, the gauges go
  blank (`--%`) on a 2.0 desk.
